## 2. 产品定位

NV8 的目标不是实现一个完整浏览器，而是实现一个面向 JavaScript 逆向
和协议复现的运行时框架。

它应当根据目标脚本实际使用的能力，动态组装出最小的、可控的、确定性的
浏览器兼容环境。

浏览器导航、请求捕获、脚本检查和运行时证据采集不属于 NV8 的职责。
这些工作由 Agent 使用 MCP 完成，并导出标准化的证据文件。NV8 从证据
文件开始工作，负责后续的加载、校验、重放、运行时补齐和协议交付。

整体链路：

```text
获取目标行为证据
  -> 分析目标脚本需要的浏览器能力
  -> 组装运行时 Profile
  -> 执行目标 JavaScript
  -> 生成 sign/token/challenge 等工件
  -> 由 Collector 发起真实请求
```

核心边界：

```text
NV8 Core
  = JS 执行、Realm 生命周期、插件编排、隔离、协议、状态、追踪、限制、诊断

NV8 插件
  = 浏览器 API、浏览器环境 Profile、目标站点行为、协议适配器、爬虫能力
```

## 3. 设计目标

### 3.1 Core 目标

- 提供类似 Flask/FastAPI 的应用工厂和插件注册模型。
- 支持 child process 和 worker thread 两种执行后端。
- Core 支持 Node.js `>=18.18`。
- 浏览器兼容能力按插件加载，而不是全部内置在 Core。
- 能够报告目标代码缺少的能力以及建议加载的插件。
- 保证 Realm、页面、Worker、Storage 和插件状态相互隔离。
- 将离线 replay、trace 和诊断作为一等能力。
- 支持浏览器无关的 signer、token、challenge 工件生成。

### 3.2 非目标

- 不在 Core 中实现所有浏览器 API。
- 不把 `vm.Context` 宣称为完整的安全边界。
- 不保证所有浏览器 Profile 在所有 Node 版本上语义完全相同。
- 不把站点专属的签名算法放入 Core。
- 不让 Core 直接承担所有爬虫调度、分页和数据落库工作。
- 不在 NV8 内设计浏览器导航、请求捕获、脚本检查或运行时证据采集。
- 不在 NV8 内直接依赖 Agent MCP；双方只通过 Evidence Bundle 文件交互。

证据采集发生在 NV8 之外：

```text
Agent MCP

  -> 导出 Evidence Bundle 文件
  -> 交给 NV8 Evidence Loader
```

NV8 读取证据之后的处理链路：

```text
Evidence Bundle
  -> 校验 Manifest、哈希和版本
  -> 加载脚本、HTML、请求响应和状态 Fixture
  -> 组装运行时 Profile 和能力插件
  -> 执行目标 JavaScript
  -> 生成协议工件
  -> Collector 发起真实请求

Protocol Layer
  -> signer、token、cookie、challenge 和请求变换

Collector Layer
  -> 真实 HTTP/WebSocket、会话、分页、重试、代理、数据存储
```

最终真实网络出口应由 Collector 负责。NV8 Runtime 负责生成窄范围的
协议工件，不直接取代完整的 Collector。

## 5. 推荐包结构

项目采用多包工作区：

```text
packages/
  core/
  plugin-sdk/
  plugin-webidl/
  plugin-dom/
  plugin-fetch-replay/
  plugin-storage/
  plugin-workers/
  plugin-rendering/
  plugin-fingerprint/
  profile-browser-edge-v150/
  profile-browser-edge-v151/
  evidence-loader/
  protocol/
  collector/
  nv8/
```

### 5.1 `@nv8/core`

Core 是框架内核，不应依赖 DOM、Fetch、Canvas 或某个具体浏览器 Profile。

Core 负责：

- 应用和 Sandbox 工厂
- child process 和 worker thread 后端
- Frame Protocol 和 typed values
- Realm 创建、重置和销毁
- 受信任模块加载
- 用户代码执行
- 插件注册和依赖解析
- 命名空间状态管理
- reset、snapshot、restore、dispose 生命周期
- 超时、内存、输出和其他限制
- trace、诊断和缺失能力报告

### 5.2 `@nv8/Plugin-sdk`

Plugin SDK 是插件作者使用的契约和工具包，提供：

- `definePlugin()`
- 插件 Manifest 类型
- Realm Context 类型
- Global Surface 注册工具
- Capability 声明工具
- 状态命名空间工具
- 插件测试基类和兼容性断言
- Node 宿主能力检查工具

### 5.3 浏览器能力插件

插件按能力域划分，不建议每个 API 方法都单独成为一个插件。

第一批可以按以下领域拆分：

```text
webidl-foundation
events
dom
navigation-storage
fetch-xhr-streams
messaging-workers
rendering-canvas
media-device
fingerprint
```

现有 `src/surface/api` 和 `src/surface/install` 可以先通过内部适配器包装成插件，第一阶段
不需要立即重写全部浏览器 API 实现。

### 5.4 环境 Profile

Profile 是插件和环境配置的组合，不应承载站点专属的签名算法。

推荐的语义命名：

```text
browser-profile-edge-v150
browser-profile-edge-v151
minimal-fetch-profile
dom-signing-profile
```

对应的 JavaScript 变量使用完整语义命名：

```js
const browserProfileForEdgeVersion150 = createBrowserProfile({
  browserFamily: "edge",
  browserVersion: 150,
});
```

命名规则：

- 不使用把产品、类型和版本号直接压缩拼接的变量名。
- 不使用无法表达职责的缩写变量名。
- 变量名应说明它是 Profile、插件、能力还是运行时配置。
- 版本号作为字段表达时，优先使用 `browserVersion: 150`。
- 版本相关变量优先使用 `browserProfileForEdgeVersion150` 这类完整语义名称。
- 新代码、包名、文档和插件 ID 均遵守此规则。

现有源码中的历史导出本次不修改，后续新增 API 不继续扩散旧式命名。

### 5.5 Evidence Loader、Protocol、Collector

这些能力应该与 Core 分包：

- `evidence-loader`：读取 Agent MCP 导出的证据文件，校验并转换为运行时
  可以消费的 Evidence Bundle。
- `protocol`：把运行时输出转换成请求参数、Header、Cookie 或 Body 变换。
- `collector`：负责真实 HTTP/WebSocket、会话、重试、分页、代理和持久化。

NV8 不包含浏览器导航、请求捕获、脚本检查和运行时证据采集实现。

### 5.6 Evidence Bundle 契约

Agent MCP 负责采集证据，NV8 负责消费证据。两者通过文件格式解耦，Core
不应直接依赖 MCP 工具或某个浏览器实现。

Evidence Bundle 至少包含：

```text
manifest.json
  -> bundle 版本、目标 URL、采集时间、文件清单、哈希、Profile 提示

scripts/
  -> 目标脚本、依赖脚本或已保存的模块源码

pages/
  -> HTML、页面元数据和必要的页面状态

network/
  -> 请求、响应、Header、Body 和 replay 所需的关联信息

runtime/
  -> cookie、storage、navigator/screen/timing 等运行时 Fixture

traces/
  -> 可选的 API trace、调用序列和调试信息
```

Evidence Loader 负责：

- 校验 Manifest、文件路径、哈希和 Bundle 版本。
- 将脚本注册到受信任模块加载器或目标代码输入层。
- 将 network 文件转换成 Fetch/XHR/Worker replay 数据。
- 将 runtime Fixture 转换成 Profile 覆盖配置和持久化状态。
- 检查证据是否缺少执行目标所需的文件或字段。
- 提供统一的 `EvidenceBundle` 对象给 Core 和插件。

Evidence Loader 不负责重新打开浏览器，也不负责主动采集新证据。

## 6. Core 应用 API

API 采用应用工厂模式：

```js
import { createApp } from "@nv8/core";
import createBrowserProfileForEdgeVersion150
  from "@nv8/profile-browser-edge-v150";

const app = createApp({
  backend: "child-process",
});

await app.loadEvidence("./evidence/example-bundle");
app.use(createBrowserProfileForEdgeVersion150());

const sandbox = await app.createSandbox({
  page: { url: "https://sandbox.test/" },
});
```

默认组合包 `nv8` 可以提供简化入口：

```js
import { createApp } from "nv8";

const app = createApp();
```

插件应显式注册。自动扫描文件系统和隐式发现插件不能成为正确性的前提。

## 7. 插件契约

插件需要声明自己的能力、依赖和生命周期：

```js
export default definePlugin({
  id: "web.fetch",
  version: "1.0.0",
  provides: ["web.fetch", "web.request", "web.response"],
  requires: ["web.url", "web.streams", "runtime.scheduler"],
  realms: ["window", "worker"],
  install(context) {},
  reset(context) {},
  serialize(context) {},
  restore(context, state) {},
  dispose(context) {},
});
```

核心字段：

- `id`：稳定的能力标识
- `version`：插件实现版本
- `provides`：插件提供的能力
- `requires`：强依赖能力
- `optional`：可选依赖能力
- `conflicts`：冲突的插件或能力
- `realms`：支持的 Realm 类型
- `hostRequirements`：需要的 Node 或宿主能力
- `install`：安装入口
- `reset`：页面或 Realm 重置行为
- `serialize`、`restore`：持久化状态行为
- `dispose`：资源清理行为

插件注册器必须在 Realm 启动前完成依赖解析、冲突检查和拓扑排序。
安装顺序必须确定，并可以在诊断信息中查看。

## 8. 插件生命周期

```text
register
  -> 校验 Manifest
  -> 解析能力依赖和冲突
  -> 检查宿主能力
  -> 拓扑排序
  -> 创建 Realm
  -> 安装构造器
  -> 安装原型和描述符
  -> 连接运行时状态
  -> 完成全局 surface 顺序
  -> activate
  -> 执行用户代码
  -> reset / serialize / restore
  -> dispose
```

插件不能依赖 JavaScript 模块的偶然 import 顺序。

全局对象和原型的修改应通过 `GlobalSurfaceRegistry` 等 Core 服务完成，避免
插件之间直接、无约束地写入 `globalThis`。

## 9. Node.js `>=18.18` 兼容策略

Node.js 兼容性属于 Core 问题，浏览器行为兼容性属于插件和 Profile 问题，
两者必须分别测试。

### 9.1 当前兼容阻塞点

当前实现明确绑定 Node `24.11.0`，主要风险包括：

1. `src/engine/realm/module-loader.js` 使用了 Node 18 不完整支持的同步
   `SourceTextModule` API。
2. `Iterator` 及相关现代内建对象在不同 Node 版本中不可统一假设。
3. `ArrayBuffer.prototype.transfer` 不能直接假设存在。
4. `Symbol.asyncDispose` 需要 feature detection。
5. 用户 JavaScript 由宿主 V8 解析，运行时 polyfill 无法补齐所有语法。
6. 当前 `package.json` 和 `.node-version` 精确声明了 `24.11.0`。

### 9.2 推荐实现路线

- Core 目标版本定义为 `>=18.18`，以 CI 验证结果为准。
- 应用启动时执行宿主能力探针。
- 增加 Node 18 可用的异步模块加载适配器。
- 新版 Node 的同步 VM 模块 API 只能作为优化路径，不能作为 Core 契约。
- Realm 创建和插件安装统一采用异步流程。
- 现代内建对象放入浏览器能力插件，不放入 Core。
- 对 disposal、transfer、worker、VM 等能力做 feature detection。
- 不支持的能力必须显式报告，不应静默返回不完整对象。
- 增加可选的源码转换扩展点，用于处理宿主 V8 无法解析的目标语法。

Core 不应承诺所有浏览器 Profile 在所有 Node 版本上语义完全一致。每个
Profile 都要发布自己的 Node 支持矩阵和降级能力说明。

### 9.3 必须建立的验证矩阵

至少测试以下版本：

```text
Node 18.18 最低基线
Node 18 最新维护版本
Node 20 最新维护版本
Node 22 最新维护版本
Node 24 最新维护版本
```

每个版本至少验证：

- child process 启动
- worker thread 启动
- Realm 创建和重置
- 普通代码执行
- Promise 执行
- 模块加载
- 插件安装
- 状态序列化和恢复
- replay 和网络捕获
- 超时和关闭

## 10. 分阶段迁移计划

- 固化当前公共行为测试。
- 增加 Node 版本矩阵。
- 找出所有 Node 版本相关假设。
- 保存当前浏览器 Profile 的 surface 快照。
- 为 bootstrap 失败增加缺失能力诊断。

### 阶段 1：抽取 Core 边界

先把通用运行时能力抽象成 Core 接口：

```text

RequestHandler

Evaluation Result

```

暂时不要拆分全部浏览器 API，先建立稳定的内核边界。

### 阶段 2：实现 Plugin SDK 和注册器 ✅

- ✅ 增加插件 Manifest（`definePlugin` API）。
- ✅ 增加能力依赖解析（`CapabilityRegistry`）。
- ✅ 增加确定性的安装阶段（`PluginInstaller`）。
- ✅ 增加 Surface Registry（`GlobalSurfaceRegistry`）。
- ✅ 增加 State Registry（`StateRegistry`）。
- ✅ 增加插件生命周期管理（`LifecycleManager`）。
- ✅ 增加插件诊断信息（结构化错误码和诊断对象）。
- ✅ 增加基础测试（依赖解析、表面冲突检测、缺失依赖检测）。
- 🔄 插件兼容性测试工具（待完善）。

### 阶段 3：适配现有实现

把现有 `src/surface/api` 和 `src/surface/install` 按能力域包装成内置插件。

首批内置插件：

```text

```

这一阶段优先保证行为不变，目标是可控组合，而不是重写整个浏览器兼容层。

### 阶段 4：创建浏览器 Profile

Profile 负责组合插件和配置值，至少包含：

- 浏览器家族和版本元数据
- navigator 和 screen 值
- rendering 值
- timing 值
- 能力可用性
- 插件版本
- 已知降级行为

### 阶段 5：增加逆向爬虫框架层

- 增加 Evidence Loader，读取并校验 Agent MCP 导出的 Evidence Bundle。
- 增加脚本、HTML、网络 replay 和运行时 Fixture 的统一输入接口。
- 增加 signer、token、challenge 协议适配器。
- 增加真实网络 Collector API。
- 增加会话、重试、分页、代理和持久化能力。

这些能力依赖 Core，但不应全部塞进 Core。

### 阶段 6：稳定插件生态

- 编写插件开发文档。
- 建立插件和 Profile 版本兼容规则。
- 增加插件和 Profile conformance suite。
- 增加最小 Profile 和完整 Profile 示例。
- 增加冷启动、热重置和插件加载性能基准。
- 明确安全边界和受信任代码边界。

## 11. 分阶段验收标准与门禁

原计划把 Core、Evidence Loader、插件注册器和内置浏览器插件的验收条件
混在同一个阶段。这会导致实现顺序与验收条件不一致，也会把 Evidence Loader
错误地变成 Core 的直接依赖。改造采用以下分阶段门禁；每一阶段必须通过门禁，
才允许进入下一阶段。

### 11.1 Baseline：行为和运行时基线

- 固化当前 `src/index.js` 导出的公共 API、默认 Edge Profile 和常用 Sandbox
  场景。
- 在当前 Node `24.11.0` 上保存 surface snapshot、评估结果、网络 replay、
  trace、reset、iframe、Worker 和关闭行为的 golden fixture。
- 记录 `bootstrap-root`、`bootstrap-worker`、`bootstrap-worklet` 的安装顺序，
  但不把该顺序直接当成未来插件顺序的契约。
- 确认现有导出和旧入口不被删除；所有迁移开关默认关闭时行为不变。
- 建立失败样本和已知差异清单，每个差异都要有 owner、严重级别和回归测试。

### 11.2 Gate 1：Core 边界和后端契约

- 可以创建不加载浏览器能力插件的基础 Sandbox，并完成执行、超时、reset、
  dispose 和结果归一化。
- child process 和 worker thread 使用同一套 `RuntimeController`、请求协议、
  生命周期事件和错误码。
- `app.loadEvidence()` 只依赖 `EvidenceLoader` 接口；具体文件格式由独立的
  `evidence-loader` 包实现，Core 不导入 MCP 或具体 Bundle schema。
- 现有 public API 由 legacy adapter 转接到 Core；新旧路径可通过启动配置选择。
- Realm 创建失败、后端断开、超时和关闭均可观测且不会留下活动句柄。

### 11.3 Gate 2：Plugin SDK 和注册器

- Manifest 校验、能力提供者解析、SemVer 范围检查、冲突检查、循环依赖检测和
  稳定拓扑排序完成。
- 生成可序列化的 Plugin lock plan，包含插件版本、能力提供者、安装顺序和
  Profile 输入摘要。
- `GlobalSurfaceRegistry`、`StateRegistry`、`RealmLifecycleRegistry` 和
  `CapabilityRegistry` 可被插件通过 SDK 使用，插件不能绕过这些服务写入全局表面。
- 缺失能力、版本冲突、Realm 不兼容和宿主能力不足都返回结构化诊断。
- 插件安装失败时按已安装顺序逆序清理，未完成的 Realm 不暴露给用户代码。

### 11.4 Gate 3：现有实现适配

- `bootstrap-root.js`、`bootstrap-worker.js` 和 `bootstrap-worklet.js` 的安装
  序列被包装为内置插件或插件组；适配阶段保持原有行为。
- 首批插件至少覆盖 Web IDL、Events、DOM、navigation/storage、fetch/XHR/streams、
  messaging/workers、rendering、media/device 和 fingerprint。
- 模块级可变状态按本计划的状态作用域迁入 Runtime Context；无法立即迁移的实现
  必须通过 legacy state adapter 显式绑定到 Sandbox/Realm，而不是继续增加新的
  全局 singleton。
- legacy-full Profile 可以复现 Baseline 的 golden fixture。

### 11.5 Gate 4：Profile 和证据输入

- Profile 能声明插件集合、版本锁、配置覆盖、能力降级和 Node 支持矩阵。
- Evidence Loader 能完成 Bundle 的路径、schema、哈希、大小、媒体类型和版本校验，
  并生成 Core 可消费的只读 `EvidenceBundle`。
- Bundle 中的脚本在明确的受信任策略下加载；默认目标脚本不能自行选择插件、
  访问宿主模块或打开真实网络。
- 缺失脚本、replay fixture 或 runtime fixture 时返回可定位的诊断，而不是静默补空值。

### 11.6 Gate 5：Protocol 和 Collector 边界

- Protocol 只消费版本化的运行时工件，并输出窄范围的 Header、Cookie、参数或
  Body 变换；不得隐式发起真实网络请求。
- Collector 独立负责真实 HTTP/WebSocket、会话、重试、分页、代理和持久化。
- 至少有一个离线 Evidence Bundle 可以端到端重放并生成可校验的协议工件。
- 真实网络出口、凭据和重试策略在诊断和权限边界中可见。

### 11.7 Gate 6：发布和生态

- Node 支持矩阵、插件/Profile 兼容矩阵、迁移指南、插件开发示例和安全边界文档
  完成。
- 插件 conformance suite、跨后端回归、负例校验和性能预算在 CI 中执行。
- 默认组合包仍能复现当前常用运行方式，且旧公共导出继续可用。
- 每次发布都产出可复现的 Profile/Plugin lock、变更记录和已知降级列表。

## 12. 主要风险

### 12.1 浏览器 API 是依赖图

DOM、Web IDL、Events、Fetch、Streams、Workers、Storage 和 Rendering 不是
完全独立的插件。插件系统必须表达硬依赖、共享注册表和安装顺序。

### 12.2 Realm 隔离

每个插件必须声明支持的 Realm 类型。Window、iframe、Worker、ServiceWorker
和 Worklet 的全局对象及生命周期并不相同。

### 12.3 状态泄漏

浏览器实现中的模块级状态可能跨 Sandbox 或 Realm 泄漏。状态必须进入
Core 管理的命名空间存储，或由插件生命周期显式管理。

### 12.4 宿主语法限制

Node 18 只能执行其 V8 能够解析的语法。运行时 polyfill 不能解决 parser
限制，因此需要源码转换扩展点或明确的语法边界。

### 12.5 安全边界

child process 提供进程级隔离，但不是完整的 OS 级沙箱。worker thread 与
宿主进程共享地址空间，只适合受信任或受控的目标代码。

## 13. 最终原则

NV8 不应被设计成一个更小的浏览器。

它应当是一个**面向能力组合的 JavaScript 运行时框架**：根据目标脚本的
实际需求装配浏览器能力，同时保持 Core 小型化、可版本化、可测试，并且
不依赖某一个固定浏览器 Profile。

## 14. 现状基线与目标映射

### 14.1 当前实现的边界

当前仓库仍然是一个以单体 bootstrap 为中心的实现，目标架构必须从这个事实
出发，不能假设多包工作区已经存在。当前主要入口和迁移职责如下：

| 当前区域 | 当前职责 | 目标归属 | 迁移原则 |
| --- | --- | --- | --- |
| `src/index.js`、`src/public/` | 公共 Sandbox API 和兼容入口 | `@nv8/core` 的 public adapter | 保留旧导出，内部逐步转接 |
| `src/engine/bootstrap/bootstrap-root.js` | Window Realm 的大量硬编码安装 | `profile` + 内置能力插件 | 先包裹调用顺序，再逐域拆分 |
| `src/engine/bootstrap/bootstrap-worker.js` | Dedicated/Shared Worker 安装 | worker realm 插件组 | 与 Window 使用同一插件契约，允许不同 surface |
| `src/engine/bootstrap/bootstrap-worklet.js` | Worklet 安装 | worklet realm 插件组 | 只安装声明支持 worklet 的能力 |
| `src/surface/install/` | 构造器、全局函数和 surface 安装 | 内置插件实现 | 不先重写 API，先增加适配层 |
| `src/surface/api/` | 浏览器行为、模块级配置和运行时状态 | 插件实现 + `StateRegistry` | 可变状态必须绑定 Runtime Context |
| `src/engine/realm/` | vm Realm 创建、模块加载和销毁 | Core realm kernel | 明确受信任模块与目标脚本边界 |
| `src/backend/child/`、`src/backend/thread/`、`src/backend/controller/` | 后端、连接和 Runtime Pool | Core backend | 后端只传输协议，不复制插件语义 |
| `src/infra/network/`、`src/backend/protocol/`、`src/infra/trace/` | replay、请求记录、工件和追踪 | Core 接口 + 独立包 | 保持真实网络出口在 Collector |
| `src/infra/fingerprint/` | 浏览器版本和环境配置 | Browser Profile | Profile 只组合能力和配置，不放站点算法 |

### 14.2 必须保持的迁移不变量

改造期间下列行为是硬约束：

- `src/index.js` 现有导出继续可用，除非另行发布 major 版本。
- 旧的 `createSandbox()` 和 `EdgeSandbox` 入口在 legacy Profile 下保持行为兼容。
- Window、iframe、Worker、ServiceWorker 和 Worklet 的 Realm 不共享可变页面状态。
- 关闭、reset、超时和后端断开后，不得留下 timer、MessagePort、Worker、observer
  或网络记录器等活动句柄。
- 默认模式不能因为插件解析失败而静默安装部分能力；要么完整使用已解析的
  Profile，要么在执行用户代码前明确失败。
- 新增插件不得通过模块 import 的偶然顺序获得正确性，也不得直接修改
  `globalThis` 或跨 Sandbox 的模块级变量。
- 迁移开关只能在 Realm 创建前决定。用户代码开始执行后禁止自动切换到另一条
  安装路径，否则同一个 Realm 可能同时拥有两套互相冲突的 surface。

### 14.3 目标包的过渡形式

在真正拆分 `packages/` 之前，可以在现有仓库内建立同名的内部目录和导出：

```text
src/engine/core/
src/plugin-sdk/
src/plugins/built-in/
src/config/profiles/
src/evidence-loader/
src/engine/compat/
```

内部目录稳定后再移动到工作区包。移动过程必须通过 package export map 和
legacy adapter 维持旧路径，不能把目录移动当作 API 变更。

## 15. Plugin SDK 详细契约

### 15.1 名称、版本和能力标识

- `plugin.id` 是全局稳定标识，使用小写的点分层命名，例如 `web.dom`、
  `runtime.scheduler`；同一应用中不得注册两个相同 ID。
- `plugin.version` 遵循 SemVer。预发布版本不能自动满足稳定版本范围，除非
  Profile 明确允许预发布版本。
- 能力 ID 与插件 ID 分开。一个插件可以提供多个能力，一个能力在一个已解析
  Profile 中只能有一个主提供者。
- `apiVersion` 表示 Plugin SDK 契约版本，与插件自身的实现版本分开。
- Realm 类型使用固定枚举：`window`、`iframe`、`worker`、`service-worker`、
  `worklet`。`iframe` 是 Window 类 Realm 的独立实例，不等于直接复用父 Realm。

### 15.2 Manifest 结构

Manifest 是可序列化的声明；函数实现不放入 JSON Manifest，而由运行时插件对象
提供。建议的最小 schema 如下：

```json
{
  "apiVersion": "1",
  "id": "web.fetch",
  "version": "1.0.0",
  "provides": [
    { "id": "web.fetch", "version": "1.0.0" },
    { "id": "web.request", "version": "1.0.0" }
  ],
  "requires": [
    { "id": "web.url", "range": ">=1.0.0 <2.0.0" },
    { "id": "runtime.scheduler", "range": ">=1.0.0" }
  ],
  "optional": [
    { "id": "runtime.trace", "range": ">=1.0.0" }
  ],
  "conflicts": [
    { "id": "legacy.fetch", "reason": "duplicate global owner" }
  ],
  "realms": ["window", "iframe", "worker"],
  "hostRequirements": {
    "node": ">=18.18",
    "features": ["vm.context", "web.streams"]
  },
  "surfaces": [
    { "target": "globalThis", "names": ["fetch", "Request", "Response"] }
  ],
  "state": {
    "scopes": ["realm", "origin"],
    "serializable": true,
    "resetPolicy": "restore"
  },
  "permissions": ["replay.read", "trace.write"]
}
```

字段规则：

- `requires` 缺失或不满足时，注册失败；`optional` 不满足时只能通过能力
  查询明确报告，不能伪造一个看似可用的空对象。
- `conflicts` 同时检查插件 ID、能力 ID 和声明的 surface 所有权。
- `hostRequirements.features` 使用 Core 能力探针的稳定 ID，不直接检查某个
  Node 内部版本号。
- `surfaces` 只声明所有权和安装目标，实际 descriptor 必须经
  `GlobalSurfaceRegistry` 注册。
- `state.scopes` 是允许使用的最高作用域，插件不能借此访问更高作用域的状态。
- `permissions` 是最小权限声明；未声明的 replay、真实网络、文件和宿主模块
  能力默认拒绝。

### 15.3 SDK 运行时对象

建议的 JavaScript 契约如下。该接口是设计目标，第一阶段可在 `src/Plugin-sdk/`
中以普通 JavaScript 实现，稳定后再导出类型定义：

```js
const plugin = definePlugin({
  manifest,
  install(context) {
    context.surfaces.define("fetch", {
      target: context.global,
      descriptor: { value: createFetch(context), writable: true },
    });
  },
  activate(context) {},
  reset(context, reason) {},
  serialize(context) {},
  restore(context, state) {},
  dispose(context) {},
});
```

`context` 至少提供：

```text
context.app
  -> 应用配置、profile、backend 信息，只读
context.realm
  -> realmId、realmType、global、document（若存在）、origin，只读引用
context.capabilities
  -> has(id)、require(id)、describe(id)，只读能力访问
context.surfaces
  -> define、defineAccessor、reserve、removeOwn、listOwned
context.state
  -> namespace、get、set、update、delete、snapshot、restore
context.lifecycle
  -> onReset、onDispose、registerResource
context.scheduler
  -> 受 Core 限制的 timer/microtask/宿主任务接口
context.trace
  -> 结构化事件记录；无权限时为拒绝对象而不是隐式全局变量
context.diagnostics
  -> 缺失能力、降级、耗时和生命周期错误记录
```

契约约束：

- Manifest 在注册时冻结，插件运行时配置通过 Profile 传入，不允许安装后修改
  依赖图。
- `app.use()` 必须发生在第一个 Sandbox 创建之前；应用锁定后再次注册抛出
  `ERR_APP_LOCKED`。需要不同插件组合时创建新的 App 或 Profile。
- `install`、`activate`、`reset`、`restore` 和 `dispose` 均允许返回 Promise，
  但 Realm 只有在所有安装和 activate 完成后才对用户代码可见。
- `serialize` 只能返回受限结构化数据；函数、Promise、Realm 对象、宿主句柄、
  循环引用和跨 Realm 对象引用都必须拒绝。
- 插件必须支持重复 `reset` 和一次性 `dispose`；Core 对重复 dispose 做幂等处理，
  但插件仍应释放自己注册的资源。

### 15.4 插件生命周期语义

| 阶段 | 允许的操作 | 失败处理 |
| --- | --- | --- |
| `register` | 校验声明和保存不可变 Manifest | App 不锁定，返回结构化注册错误 |
| `plan` | 解析依赖、冲突、宿主要求和 surface 所有权 | 不创建 Realm，不执行插件代码 |
| `install` | 注册构造器、descriptor、状态命名空间和资源 | 按逆序执行已完成插件的清理 |
| `activate` | 连接 Realm 状态和 Profile 配置 | Realm 标记失败，不交给用户代码 |
| `reset` | 清理页面状态并按策略恢复快照 | 中止本次 reset，记录插件 ID 和原因 |
| `serialize`/`restore` | 导出或导入声明的持久化状态 | schema 不匹配时拒绝恢复，不静默丢字段 |
| `dispose` | 取消资源、删除自有 surface、释放状态 | 继续清理其他插件并聚合错误 |

安装失败必须返回 `PluginInstallError`，包含 `pluginId`、`phase`、原始错误、已
完成插件列表和 cleanup 结果。错误对象不能把目标脚本源码或凭据写入默认日志。

## 16. 能力依赖解析与安装计划

### 16.1 解析规则

解析器输入是 Profile 声明的插件集合、应用级覆盖和当前 Realm 类型，输出不可变
的 `PluginLockPlan`。解析步骤固定为：

1. 校验所有 Manifest 的字段、ID、SemVer、Realm 和权限。
2. 按能力 ID 收集提供者，并为每个必需能力选择唯一提供者。
3. 检查 SemVer 范围、Profile 的显式 pin 和插件冲突。
4. 递归展开强依赖；可选依赖只在存在兼容提供者时连接。
5. 检测循环依赖、重复 surface 所有权和不支持的 Realm。
6. 对依赖图做确定性拓扑排序：优先满足依赖，再以插件 ID 的字典序作为平局
   规则；不能使用文件系统枚举或 import 顺序作为排序依据。
7. 生成 lock plan，并计算插件 Manifest、Profile 配置和宿主能力摘要的哈希。

伪代码：

```text
validate(manifests, profile, hostCapabilities)
providers = indexProviders(manifests)
for requirement in profile.requiredCapabilities:
  provider = selectProvider(requirement, providers, profile.pins)
  require provider
  visit(provider)
visit(plugin):
  if plugin is visiting: error CIRCULAR_DEPENDENCY
  if plugin is visited: return
  mark visiting
  for dependency in sort(plugin.requires by capability id):
    visit(selectProvider(dependency))
  check optional dependencies, conflicts, realm and host requirements
  mark visited
plan = stableTopologicalOrder(visited, tieBreak=plugin.id)
checkSurfaceOwnership(plan)
return freezeLockPlan(plan)
```

### 16.2 提供者选择和冲突策略

- 同一能力存在多个满足版本范围的提供者时，优先使用 Profile 的显式 pin；
  没有 pin 时选择最高兼容版本，再以插件 ID 作稳定平局规则。
- 两个插件都声明同一个可写 global descriptor 的所有权时，默认失败。覆盖行为
  必须由 Profile 明确声明，并记录原所有者、覆盖者和原因。
- `conflicts` 是硬冲突，不支持“后安装者覆盖”作为隐式解决方案。
- 循环依赖即使在运行时理论上可工作也必须失败；需要共享基础能力时应抽取
  第三个基础插件。
- lock plan 必须可序列化、可审查、可复现。运行时不得根据网络、当前目录文件
  顺序或随机值重新选择 provider。

### 16.3 诊断错误码

至少定义以下稳定错误码：

```text
PLUGIN_INVALID_MANIFEST
PLUGIN_DUPLICATE_ID
CAPABILITY_MISSING
CAPABILITY_VERSION_UNSATISFIED
CAPABILITY_PROVIDER_AMBIGUOUS
PLUGIN_CONFLICT
PLUGIN_CIRCULAR_DEPENDENCY
REALM_UNSUPPORTED
HOST_REQUIREMENT_UNSATISFIED
SURFACE_OWNERSHIP_CONFLICT
PLUGIN_INSTALL_FAILED
PLUGIN_RESET_FAILED
PLUGIN_STATE_INVALID
```

每个错误至少包含 `code`、`message`、`pluginId` 或 `capabilityId`、相关版本范围、
`realmType`、建议动作和可安全展示的依赖路径。诊断输出应支持机器读取和人类阅读。

## 17. Global Surface 与状态隔离

### 17.1 GlobalSurfaceRegistry

所有由插件新增或修改的全局属性、原型属性和 Web IDL descriptor 都必须经过
`GlobalSurfaceRegistry`：

```text
reserve(owner, targetKind, propertyName)
define(owner, target, propertyName, descriptor, options)
defineAccessor(owner, target, propertyName, getter, setter, options)
removeOwn(owner, target, propertyName)
listOwned(owner)
```

Registry 必须记录 owner、target Realm、descriptor、可配置性和安装阶段。规则如下：

- 未声明的名字不能写入；声明只代表允许申请，不代表自动拥有。
- 已有 owner 的名字再次申请时必须经过冲突策略检查。
- 删除操作只能删除当前插件自己创建的 descriptor，不得删除用户代码或其他插件
  的属性。
- surface 安装顺序来自 lock plan；最终排序和 descriptor snapshot 必须可追踪。
- `globalThis`、Window facade、iframe facade 和 Worker global 的所有权分别记录，
  不能因对象看起来相同而混用。

### 17.2 StateRegistry 作用域

状态键至少由以下维度组成：

```text
(appId, sandboxId, realmId, pluginId, scope, key)
```

允许的 scope 从窄到宽为：

```text
resource -> realm -> page -> origin -> sandbox -> app -> process
```

默认规则：

- `resource` 状态属于单个 timer、observer、channel 或请求对象。
- `realm` 状态只在一个 Window/Worker/Worklet Realm 内可见。
- `page` 状态在同一页面 reset 前后按插件策略处理，不跨 Sandbox。
- `origin` 状态只允许同一 Sandbox 的同源页面使用；Storage 等能力显式选择此级别。
- `sandbox` 状态可供该 Sandbox 的多个 Realm 使用，但不能被其他 Sandbox 读取。
- `app` 和 `process` 只允许不可变缓存、编译产物或显式声明的共享资源，禁止存放
  cookie、页面状态、目标脚本变量或会话凭据。

插件 SDK 不向插件暴露裸的模块级 Map。迁移前确实需要模块级缓存时，必须使用
`WeakMap<RuntimeContext, State>` 或 Core 提供的命名空间，并写明 scope、清理责任
和并发策略。

### 17.3 reset、snapshot 和 dispose

- `reset({ preserve })` 先停止用户可见任务，再调用插件 reset，最后重建或恢复
  声明的 page/origin 状态；未声明的状态全部丢弃。
- `snapshot` 只包含插件通过 `serialize` 声明的字段，并带有插件版本和 state schema
  版本。恢复时先做兼容检查，再调用 `restore`。
- `dispose` 以逆序停止插件，取消 timer、observer、MessagePort、Worker、网络
  recorder、object URL 和临时文件；Core 最后关闭 Realm 和后端。
- reset/dispose 期间禁止用户代码重新进入同一个正在销毁的 Realm；否则返回
  `ERR_REALM_CLOSING`。
- 一个插件清理失败不能跳过其他插件清理；Core 聚合错误，最终以可诊断的状态
  关闭资源。

### 17.4 DOM bookkeeping 的实现约束

任何依赖 DOM 变更维护索引的插件都应优先读取其内部节点状态和 mutation record，
不能在 mutation hook 中通过公开的 `Document.defaultView`、公开 collection 或
可能被插件代理的 getter 回读同一 Realm。确需公开 API 回读时必须同时满足：

- 使用 Realm 级重入保护；
- 将同步刷新合并为一次待处理任务，避免递归和重复扫描；
- `try/finally` 恢复保护状态；
- 对追加、删除、移动和导航分别有回归测试。

这条约束覆盖 iframe frame-index bookkeeping 等现有路径，属于 DOM 插件的实现
契约，而不是 Core 通过全局变量兜底的行为。

## 18. Evidence Bundle 详细规范

### 18.1 目录布局

```text
evidence/example-bundle/
  manifest.json
  scripts/
    main.js
    dependencies/module-a.js
  pages/
    entry.html
    metadata.json
  network/
    replay.json
    bodies/response-001.bin
  runtime/
    cookies.json
    storage.json
    environment.json
  traces/
    api-trace.jsonl
```

Bundle 是离线输入。Loader 不导航、不打开浏览器、不调用 MCP、不主动联网，也
不执行 Bundle 中的目标脚本来完成校验。

### 18.2 Manifest 示例

```json
{
  "schemaVersion": "1.0",
  "bundleId": "example-2026-01-01",
  "target": {
    "url": "https://target.test/sign",
    "origin": "https://target.test",
    "capturedAt": "2026-01-01T00:00:00.000Z"
  },
  "profile": {
    "id": "browser-profile-edge-v150",
    "versionRange": ">=1.0.0 <2.0.0",
    "requiredCapabilities": ["web.dom", "web.crypto"],
    "pluginPins": {
      "web.dom": "1.0.0"
    }
  },
  "files": [
    {
      "path": "pages/entry.html",
      "role": "page",
      "mediaType": "text/html",
      "bytes": 1280,
      "sha256": "<64 lowercase hex characters>"
    },
    {
      "path": "scripts/main.js",
      "role": "script",
      "mediaType": "text/javascript",
      "bytes": 4096,
      "sha256": "<64 lowercase hex characters>"
    }
  ],
  "entrypoints": ["scripts/main.js"],
  "replay": {
    "fixture": "network/replay.json",
    "matching": "method-url-body-sha256"
  },
  "redaction": {
    "secretsRemoved": true,
    "tracePolicy": "metadata-only"
  }
}
```

`<64 lowercase hex characters>` 只用于说明格式，真实 Bundle 必须填写实际摘要。
Manifest 自身不包含递归的 Bundle 摘要；如需完整 Bundle digest，定义为对规范化
Manifest（排除 digest 字段）和按字典序排列的文件摘要列表计算 SHA-256。规范化
规则必须固定为 UTF-8、对象键字典序、数组顺序保持语义顺序、无额外空白和 LF 换行。

### 18.3 Loader 输入输出

```js
const evidenceBundle = await loadEvidenceBundle(bundlePath, {
  limits: {
    maxFiles: 10_000,
    maxFileBytes: 50 * 1024 * 1024,
    maxTotalBytes: 512 * 1024 * 1024,
    maxManifestBytes: 2 * 1024 * 1024,
  },
  trustedScriptPolicy: "registered-only",
});

const app = createApp({ backend: "child-process" });
await app.loadEvidence(evidenceBundle);
```

`EvidenceBundle` 是只读对象，至少包含：

```text
manifest
files(path, role, mediaType, bytes, sha256)
scripts(entrypoints, source/read-only handles)
pages(html, metadata)
network(replay records and body handles)
runtime(cookie/storage/environment fixtures)
traces(optional redacted records)
verification(schema, hashes, limits, verifiedAt)
```

`app.loadEvidence(path)` 可以接受路径，也可以接受已由独立 Loader 校验的对象；
Core 只依赖上述抽象接口，不依赖 manifest 的磁盘布局。

### 18.4 必须执行的校验

Loader 必须在任何内容暴露给 Core 或插件前完成完整校验：

- 只允许相对路径；拒绝绝对路径、空路径、`..`、反斜杠混用和 NUL 字符。
- 拒绝符号链接、硬链接逃逸、重复路径、Manifest 未列出的文件和缺失文件。
- 校验 `schemaVersion`、必需字段、URL/origin、一致的媒体类型、文件大小和 SHA-256。
- 限制文件数量、单文件大小、总大小、JSON 深度、数组长度、脚本入口数量和
  replay body 大小，超限返回 `EVIDENCE_LIMIT_EXCEEDED`。
- 不根据文件扩展名决定是否执行；脚本必须被 manifest 明确标记并经过 trust policy。
- 目标脚本默认只能访问虚拟浏览器 API；不能通过 Bundle 指定额外插件、Node 模块、
  `process`、文件系统、环境变量或真实网络权限。
- cookie、Authorization、个人信息和 trace 参数在导出前脱敏；Loader 不负责猜测
  哪些秘密可以安全恢复。

错误码至少包括：

```text
EVIDENCE_NOT_FOUND
EVIDENCE_INVALID_MANIFEST
EVIDENCE_SCHEMA_UNSUPPORTED
EVIDENCE_PATH_UNSAFE
EVIDENCE_SYMLINK_REJECTED
EVIDENCE_FILE_MISSING
EVIDENCE_FILE_UNDECLARED
EVIDENCE_HASH_MISMATCH
EVIDENCE_MEDIA_TYPE_MISMATCH
EVIDENCE_LIMIT_EXCEEDED
EVIDENCE_ENTRYPOINT_INVALID
EVIDENCE_TRUST_POLICY_REJECTED
EVIDENCE_FIXTURE_INVALID
```

### 18.5 Network replay 记录

Replay 记录必须支持确定性匹配，不以“最接近的请求”静默命中。最小记录包括：

```json
{
  "id": "request-001",
  "request": {
    "method": "POST",
    "url": "https://target.test/api",
    "headers": [{ "name": "content-type", "value": "application/json" }],
    "bodySha256": "<hex>"
  },
  "response": {
    "status": 200,
    "statusText": "OK",
    "headers": [{ "name": "content-type", "value": "application/json" }],
    "bodyFile": "network/bodies/response-001.bin"
  },
  "sequence": 1,
  "repeat": "once"
}
```

匹配键由 fixture 声明，可以是 method+URL、method+URL+body digest 或带受控 header
子集的组合。未命中、重复次数耗尽、顺序错误和 body 摘要不匹配必须分别记录结果，
不准自动发起真实请求。真实请求由 Collector 另行负责。

### 18.6 Schema 和兼容策略

- `schemaVersion` 遵循 major/minor 规则：major 不兼容时 Loader 拒绝，minor
  增加可选字段时旧 Loader 可以继续读取但必须记录 warning。
- Bundle 的 Profile/Plugin lock 是输入约束，不是授权目标脚本安装插件的机制。
- Loader 与 Core 的版本分别记录；错误消息包含两者版本和支持范围。
- Bundle 验证结果可缓存，但缓存键必须包含 Bundle digest、Loader 版本和 limits 摘要。

## 19. 应用、Sandbox 与后端 API

### 19.1 App 生命周期

推荐 API 的语义如下：

```js
const app = createApp({
  backend: "child-process",
  profile: browserProfileForEdgeVersion150,
  limits: { timeoutMs: 5_000, maxHeapBytes: 256 * 1024 * 1024 },
});

app.use(webIdlPlugin());
app.use(domPlugin());
await app.loadEvidence("./evidence/example-bundle");

const sandbox = await app.createSandbox({
  page: { url: "https://sandbox.test/", html: "" },
});
const result = await sandbox.run("document.title");
await sandbox.reset();
await sandbox.dispose();
await app.dispose();
```

- `createApp` 只创建配置和注册表，不创建 Realm。
- `use` 注册插件或 Profile 展开的插件，返回 App 以便链式配置；发现错误时立即
  失败，依赖和宿主能力在 `createSandbox` 前的 plan 阶段再次完整检查。
- `loadEvidence` 校验或接收只读 Bundle，可在创建 Sandbox 前调用；Bundle 绑定到
  App 后不能被目标脚本修改。
- `createSandbox` 固化 Profile、lock plan、limits 和 backend，之后 App 仍可创建
  同一配置的新 Sandbox，但不能改变已固化配置。
- `reset` 不改变插件集合和 lock plan；需要不同组合必须创建新 App。
- `dispose` 是幂等的；已 dispose 的 App/Sandbox 的新操作返回稳定错误码。

### 19.2 Backend 共同协议

Child process 和 worker thread 的差异只在隔离和传输实现，不在用户可见语义。请求
Frame 至少包含：

```text
protocolVersion
requestId
sandboxId
operation (create/evaluate/reset/snapshot/restore/dispose/diagnose)
payloadLength
payload
```

响应至少包含：

```text
protocolVersion
requestId
status (ok/error)
resultType
payloadLength
payload or structured error
```

协议必须限制 frame 长度、嵌套深度、字符串和二进制大小，拒绝截断、重复 requestId、
未知 operation 和版本不兼容的帧。错误归一化不能丢失 `code`、`phase`、`requestId` 和
后端信息。

### 19.3 受信任模块与目标脚本

内部 bootstrap、插件实现和模块 bundle 属于受信任代码，目标脚本属于不受信任或
受控代码。两者必须使用不同的加载路径、权限和缓存：

- 内部模块只允许来自已安装包的 allowlist，禁止 `node:`、任意 `file:` 和动态导入。
- 目标脚本只能通过明确的 evaluate/module 输入接口进入 Realm；默认关闭宿主导入。
- 编译缓存可以在 process scope 共享源文本或不可变编译产物，但不能共享 Module
  实例、Context、函数、Storage 或页面状态。
- 受信任插件不能把目标脚本输入拼接进内部模块源码。

## 20. Node.js 兼容层实施方案

### 20.1 当前阻塞点和迁移顺序

当前 `package.json` 与 `.node-version` 精确绑定 Node `24.11.0`，而现有
`src/engine/realm/module-loader.js` 直接使用同步 `vm.SourceTextModule`、`instantiate`、
`moduleRequests`、`linkRequests` 和 cached data。这个实现不能在未验证的情况下
直接把 engines 放宽到 `>=18.18`。

兼容改造按以下顺序进行：

1. 增加 `HostCapabilities` 探针，记录 Node 版本、V8 版本、vm module API、worker、
   structured clone、timer disposal 和二进制能力。
2. 把模块加载封装为异步 `ModuleLoader` 接口。Node 24 的同步快速路径只能是内部
   优化，不能成为 Core 契约。
3. 为 Node 18 提供经过 CI 验证的异步加载路径；如果某个能力没有可接受的实现，
   返回 `HOST_REQUIREMENT_UNSATISFIED`，不能返回半初始化 Realm。
4. 将 `SOURCE_CACHE`、编译缓存和 Realm Module 实例分开：前两者可以按安全规则共享，
   Module 实例必须绑定当前 Context。
5. 所有 bootstrap、插件安装和 Realm 创建 API 保持异步；不允许调用方依赖 Node 24
   的同步模块行为。
6. 只有 Node 18.18 到 Node 24 的矩阵全部通过后，才更新 `engines` 和 `.node-version`
   的发布策略。

### 20.2 能力探针

探针返回稳定 feature ID，而不是让插件自己读取宿主对象：

```js
export function detectHostCapabilities() {
  return Object.freeze({
    nodeVersion: process.versions.node,
    v8Version: process.versions.v8,
    features: Object.freeze({
      "vm.context": typeof vm.createContext === "function",
      "vm.source-text-module": typeof vm.SourceTextModule === "function",
      "worker.thread": typeof Worker === "function",
      "structured.clone": typeof structuredClone === "function",
      "array-buffer.transfer": typeof ArrayBuffer.prototype.transfer === "function",
      "symbol.async-dispose": typeof Symbol.asyncDispose === "symbol",
    }),
  });
}
```

实际实现不能因为某个全局对象被隐藏或 polyfill 而简单判断可用性；探针需要执行
最小 smoke test，并将 `available`、`broken`、`reason` 分开记录。插件只查询
`context.host.has("vm.context")` 等稳定 ID。

### 20.3 宿主能力降级

- `ArrayBuffer.prototype.transfer`、`Symbol.asyncDispose`、Iterator helpers 等不是
  Core 的必需能力；使用者必须声明 fallback 或显式缺失。
- 用户脚本语法由当前 V8 parser 决定，运行时 polyfill 不能补齐 parser 不支持的语法。
  可选的源码转换器必须是明确注册的 extension，并在 trace 中记录转换前后摘要。
- 不能把 Node 内置模块自动暴露给目标脚本。宿主模块加载属于受信任 loader 权限。
- 各 Profile 发布自己的 Node 支持矩阵；Core 支持版本不代表每个 Profile 的所有
  browser surface 都一致。

### 20.4 验证矩阵

至少在以下版本执行相同测试集：

```text
Node 18.18 最低基线
Node 18 最新维护版本
Node 20 最新维护版本
Node 22 最新维护版本
Node 24 最新维护版本
```

每个版本和后端组合至少验证：

- child process 和 worker thread 启动、重连、关闭；
- root、iframe、worker、service-worker、worklet Realm 创建；
- 普通代码、Promise、模块和受限动态导入；
- 插件 plan、安装、reset、snapshot/restore、dispose；
- replay、请求记录、trace 和错误归一化；
- 超时、最大输出、最大 heap、Frame 长度和嵌套深度限制；
- Node 版本不满足时的结构化失败，而非静默降级。

## 21. 渐进式迁移实施计划

### 21.1 迁移开关

迁移开关在应用启动时读取，并纳入 lock plan 哈希：

```text
NV8_RUNTIME_MODE=legacy|plugin
NV8_PROFILE_ID=legacy-full|browser-profile-edge-v150|...
NV8_PLUGIN_PLAN=auto|locked:<path>
NV8_HOST_DIAGNOSTICS=off|basic|full
```

- 默认值在迁移完成前为 `legacy`，确保旧行为不变。
- `plugin` 模式必须在 Realm 创建前完成 plan 和所有校验。
- 生产环境推荐使用 `locked:<path>`，拒绝运行时重新解析出不同插件版本。
- 开发环境允许 `auto`，但必须把实际 plan 写入诊断，便于生成 lock 文件。
- 用户代码执行后如果插件安装失败，只能销毁 Realm 并返回错误，禁止切换到 legacy。

### 21.2 现有安装序列映射

第一轮只建立适配器和映射表，不立即移动 5500 多个实现文件。映射表由代码生成
并在 CI 校验，至少包括以下能力域：

| 能力插件 | 现有来源 | 依赖方向 | 首轮策略 |
| --- | --- | --- | --- |
| `webidl-foundation` | `src/engine/webidl/`、基础 descriptor 安装 | runtime kernel | 先提供 Registry 和 native function 服务 |
| `events` | event target、event、mutation observer | webidl-foundation | 保持构造器和 dispatch 行为 |
| `dom` | `src/surface/api/dom/`、DOM install 文件 | webidl、events | 先整体适配，再按 Document/Element 拆分 |
| `navigation-storage` | navigation、location、history、storage、cookies | webidl、dom | 状态按 origin/sandbox 绑定 |
| `fetch-xhr-streams` | fetch replay、XHR、Request/Response、streams | URL、scheduler、trace | replay 只读，真实网络交给 Collector |
| `messaging-workers` | messaging、worker、broadcast、service worker | events、scheduler | 每个 worker 建立独立 Realm Context |
| `rendering-canvas` | canvas、WebGL、GPU、image、media | dom、Profile | 配置来自 rendering Profile |
| `media-device` | media、device、codec、speech | dom、Profile | 明确能力缺失和降级 |
| `fingerprint` | `src/infra/fingerprint/`、navigator/screen/timing | webidl、Profile | 只提供 Profile 数据，不安装站点算法 |

每个映射条目还必须记录：安装入口、全局 surface、模块级状态、资源清理动作、
支持的 Realm、现有测试和迁移 owner。未完成登记的 install 文件不能被标记为
Plugin mode 已覆盖。

### 21.3 阶段任务、产物和回滚点

| 阶段 | 主要任务 | 必须产物 | 回滚方式 |
| --- | --- | --- | --- |
| 0 基线 | 记录公共行为、安装顺序、Node 24 指标 | golden fixtures、surface snapshot、差异清单 | 保留当前入口和版本 |
| 1 Core 边界 | 抽取 controller、backend、Realm、结果和限制接口 | `RuntimeController`、Frame schema、legacy adapter | 默认切回 `legacy` |
| 2 SDK/Registry | Manifest、Capability、Surface、State 和生命周期 | `PluginLockPlan`、诊断错误码、SDK smoke tests | Plugin plan 不启用 |
| 3 内置适配 | 包装 root/worker/worklet 安装，迁移模块状态 | `legacy-full` Plugin Profile、映射表 | 单 Profile 关闭，保留旧 bootstrap |
| 4 Profile | 组合插件、配置 fingerprint、声明支持矩阵 | Edge profiles、Profile lock、surface diff | 使用上一版 Profile lock |
| 5 Evidence | Loader、schema、replay fixture、runtime fixture | schema、负例集、离线端到端样例 | 不加载 Evidence，使用旧输入 |
| 6 Protocol/Collector | 窄工件接口和真实网络边界 | protocol adapter、Collector contract | 工件版本回退，禁止绕过边界 |
| 7 发布 | 文档、conformance、性能和安全审查 | 兼容矩阵、迁移指南、发布包 | 保留上一 major/minor 版本 |

每个阶段结束必须通过对应 Gate，并保存可重放的 lock、fixture 和诊断。回滚是
切换到上一阶段的已发布 adapter/Profile，不使用 `git reset` 或删除用户数据来
实现回滚。

### 21.4 逐域迁移顺序

推荐顺序是：

1. Core services：错误、限制、scheduler、trace、surface、state、lifecycle。
2. Web IDL 和 Events：先建立所有其他插件共享的 descriptor 和事件基础。
3. URL、文本、Blob、Streams 等低状态基础能力。
4. DOM 和 Window surface；包含 iframe、mutation、collection 的内部状态迁移。
5. navigation、Storage、cookie、Fetch/XHR 和 replay。
6. Messaging、Worker、ServiceWorker、Worklet 等多 Realm 能力。
7. Rendering、Media、Device、Fingerprint 和 Profile 覆盖。
8. Evidence、Protocol、Collector 的独立包和端到端流程。

依赖较多的能力不得为了“先拆文件”而提前成为独立插件；插件边界按行为和状态
所有权划分，而不是按单个 API 文件数量划分。

### 21.5 每个插件的迁移清单

插件迁移完成前必须回答：

- 提供哪些 capability、支持哪些 Realm、依赖哪些版本范围？
- 写入了哪些 global/prototype descriptor，所有权是否登记？
- 使用了哪些模块级变量、Map、Set、WeakMap、timer 或宿主句柄？
- 状态的 scope、reset policy、serialize schema 和 dispose 动作是什么？
- 在 Node 18、20、22、24 和两个后端上的结果是否一致？
- 缺少可选能力时页面可见行为是什么，是否有明确诊断？
- 是否有 surface snapshot、行为 fixture、并发隔离和失败清理测试？

未完成清单的插件只能在内部实验 Profile 中启用，不能进入默认组合包。

## 22. 测试与验证策略

### 22.1 测试层次

- **单元测试**：Manifest 校验、SemVer、依赖图、排序、descriptor 所有权、StateRegistry
  scope、Bundle 路径和 hash 校验。
- **插件契约测试**：对每个插件统一执行 install、activate、缺失依赖、reset、snapshot、
  restore、dispose、重复调用和错误清理。
- **Realm 集成测试**：Window/iframe/Worker/ServiceWorker/Worklet 的 global surface、
  origin 隔离、消息、Storage、timer 和关闭行为。
- **后端一致性测试**：同一 fixture 在 child process 和 worker thread 上执行，比较
  typed result、错误码、trace、网络记录和资源关闭结果。
- **golden 测试**：对当前常用 Sandbox 保存 surface、descriptor、结果、请求、trace
  和导航 fixture；插件迁移只能产生显式审查过的差异。
- **Evidence 负例测试**：路径逃逸、符号链接、缺文件、未声明文件、hash 错误、超限、
  schema 版本、恶意 JSON 深度和不允许的脚本权限。
- **安全测试**：目标脚本尝试 Node import、文件访问、真实网络、prototype 越界、
  跨 Sandbox 读取和后端 Frame 注入时必须被拒绝或被限制。

### 22.2 必测行为集合

每个默认 Profile 至少覆盖：

```text
基础执行、Promise、异常和结果归一化
Window/iframe 的 document、defaultView、contentWindow、frame index
DOM append/remove/move、mutation、collection 和 reset
Storage/cookie/origin 隔离
fetch/XHR replay、未命中和请求记录
Dedicated/Shared/Service Worker 与消息生命周期
Worklet 安装、注册和 dispose
surface descriptor、toString、原生函数标记和 prototype 链
trace、diagnose、timeout、heap/output/frame 限制
并发 Sandbox、重置后状态、关闭后句柄计数
```

### 22.3 失败和回归判定

- 任何安全边界失败、跨 Sandbox 泄漏、错误网络出口、资源句柄泄漏或重复 surface
  都是阻塞问题。
- 行为差异必须按 `intentional`、`profile-specific`、`bug` 分类；只有前两类经过
  记录和批准后可更新 golden fixture。
- 测试结果记录 Node、V8、backend、Profile lock、Plugin lock 和 Evidence digest，
  使失败可复现。
- 每次变更至少运行受影响插件的契约测试、默认 Profile smoke test 和后端一致性测试。

### 23.1 诊断对象

```json
{
  "code": "HOST_REQUIREMENT_UNSATISFIED",
  "message": "The selected profile requires a host feature that is unavailable",
```

### 23.2 生命周期事件

### 23.3 Trace 和网络记录边界

- trace 默认关闭或使用受限摘要；完整参数必须由调用方显式开启，并支持字段脱敏。
- 网络记录只记录请求结果、匹配状态和必要元数据；Authorization、Cookie、token
  和 body 默认摘要化或删除。
- 诊断不能通过公开的 Window API 写回页面，避免观察逻辑改变页面行为。
- 诊断读取是只读操作，不能触发新的插件安装、导航、网络请求或状态恢复。

## 24. 性能、资源和缓存预算

### 24.1 基线和预算

Baseline 先测量当前实现的冷启动、热 reset、单次 evaluate、首个 iframe、首个 Worker、
峰值 RSS、Realm heap、插件/模块加载耗时和关闭耗时。下列是第一版相对预算，实际
数值在基线测量后写入 CI 配置：

| 指标 | 初始预算 | 超预算处理 |
| --- | --- | --- |
| 默认 Profile 冷启动 | 不超过 legacy 基线的 115% | 检查重复安装和解析缓存 |
| 已锁定 Profile 热 reset | 不超过 legacy 基线的 110% | 检查状态序列化和资源清理 |
| 单次 evaluate 延迟 | 不超过 legacy 基线的 105% | 只允许在结果等价时优化 |
| 峰值 RSS/Realm heap | 不超过 legacy 基线的 110% | 检查跨 Realm 引用和缓存作用域 |
| 关闭耗时 | 不超过 legacy 基线的 120% | 检查未结束 timer、worker 和 channel |
| Plugin plan 重复执行 | 使用 lock 后不应重复解析 | 检查 lock/cache key |

预算是回归门槛，不是对所有机器的绝对保证。CI 同时记录硬件、Node、backend、
Profile lock 和缓存状态。

### 24.2 缓存作用域

- Manifest 校验、依赖解析和不可变 Profile lock 可以在 App 或 process 级缓存；缓存
  键必须包含输入摘要、SDK 版本和宿主能力摘要。
- 源文本、`vm.Script` 或安全编译产物可以按 process 级缓存，但不能缓存 Realm 绑定
  的 Module、函数和全局对象。
- Network replay fixture 可以共享只读 bytes；请求计数、顺序、abort 和 recorder
  必须是 Sandbox/Realm 级状态。
- 任何缓存都必须有大小上限、LRU 或明确的生命周期，不允许以“长期进程”作为无限
  内存的理由。
- pre-warm shell 只能预热无页面状态的 Realm 模板；接入用户代码或 runtime fixture
  前必须创建全新的状态容器。

### 24.3 并发限制

Core 根据 `maxHeapBytes`、后端类型和估算的 Realm 成本决定并发上限。达到限制时
返回 `LIMIT_REALM_CAPACITY`，不得继续创建后再依赖 OOM。每个后端还必须限制：

```text
同时 Sandbox 数
每个 Sandbox 的 child Realm 数
未完成 evaluate 数
网络 replay body 总量
trace entries
Frame queue bytes
```

## 25. 版本、兼容与发布策略

### 25.1 版本层级

- Core public API、Frame Protocol、Plugin SDK 和 Evidence schema 分别有自己的
  major/minor/patch 版本，不用一个包版本隐式代表全部兼容性。
- Plugin SDK major 变化需要插件重新声明 `apiVersion`；Core 在 plan 阶段拒绝未知
  major，而不是在安装中途失败。
- Profile 版本包含浏览器家族、浏览器版本、插件 lock、配置 schema 和已知降级；
  同一 Profile 的 patch 版本不得改变未声明的页面行为。
- Protocol 工件带 schema version；Collector 必须声明可消费的范围。

### 25.2 向后兼容

- 旧公共导出通过 compatibility adapter 维护；新 API 不要求用户一次性迁移到
  `createApp()`。
- legacy-full 是迁移期间的内置 Profile，不作为永久掩盖架构问题的方式；它必须
  继续接受相同的回归测试，并在发行说明中标明维护状态。
- 废弃 API 至少经历一个 minor 版本的 warning 和迁移文档，major 版本才可以移除。
- lock 文件应记录生成工具版本、平台、Node 范围、插件版本和 Profile digest，发布
  包中同时保存上一版可回滚 lock。

### 25.3 支持矩阵

每个发布包都要公开以下矩阵：

```text
Core version x Node version x backend
Profile version x Node version x realm type
Plugin version x Plugin SDK apiVersion
Evidence schema x Loader version
Protocol schema x Collector version
```

矩阵中的 `supported`、`degraded`、`unsupported` 必须有自动化测试或明确的原因，
不能只写一个宽泛的 `>=18.18`。

## 26. 安全边界和威胁模型

### 26.1 信任层级

```text
Level 0: Core、后端、Frame parser、限制和状态隔离实现
Level 1: 受审查的内置插件和 Profile
Level 2: 受控的第三方插件
Level 3: Evidence 中的目标脚本、HTML、replay body 和 runtime fixture
```

Level 3 内容不得反向提升为 Level 0/1 权限。第三方插件虽然是受信任安装代码，
也必须经过 Manifest、权限、surface、state、依赖和 conformance 审查。

### 26.2 隔离声明

- `vm.Context` 不是完整安全边界；Core 文档不得把它宣传成阻止恶意代码逃逸的
  OS sandbox。
- worker thread 与宿主共享地址空间，适用于受控目标代码，不适合作为不可信代码
  的强安全边界。
- child process 提供进程级故障隔离，但不是 OS 级沙箱；需要对抗恶意目标时必须
  由部署方提供容器、seccomp、权限账户、网络策略和资源 cgroup。
- Frame Protocol、Evidence Loader 和 Collector 都必须做长度、深度、超时、路径、
  权限和凭据保护，不能把隔离责任全部交给 vm。

### 26.3 权限和网络

- 默认 Profile 不允许目标脚本访问真实网络；Fetch/XHR 只能访问显式 replay fixture。
- Protocol 可以生成工件，但不拥有 Collector 的 socket、代理、凭据和重试权限。
- Collector 的真实网络权限、目标域名 allowlist、代理和持久化位置由部署配置控制，
  不能被网页脚本或 Evidence manifest 修改。
- 所有写文件、加载 Bundle、导出 trace 和读取 runtime fixture 的行为都要经过
  路径和权限检查。

#### 关键 Bug 修复记录

在 Phase 2 实施过程中，发现并修复了三类影响运行时稳定性的问题：

##### Bug 1: NV8 自身的 DOM parser 缺陷（已修复）

**问题描述**：
- `<?xml version="1.0" encoding="utf-8"?>` 触发了 NV8 `parseFragment()` 的死循环
- 这是 NV8 DOM shim 的真实 bug，和 iv8 是否使用同一个 JavaScript 引擎无关
- iv8 如果使用了更完整的 HTML parser，或者把这段内容按文本/comment 处理，就不会出现

**修复方案**：
- 位置：`src/surface/api/dom/html-parser.js:49-61`
- 在 `parseFragment()` 中添加对 `<?...?>` 处理指令的显式处理
- 检测到 `<?xml` 或 `<?` 开头时，跳过整个处理指令直到 `?>`
- 对格式错误的处理指令（缺少 `?>`），直接跳到输入末尾

**验证状态**：✅ 已修复并验证

##### Bug 2: NV8 harness 的预加载导致时序失真（设计问题）

**问题描述**：
- 原来的 NV8 harness 在 punishment driver 启动前就直接 eval 了 `nc.js`
- 这样 AWSC 内部状态已经是 `loaded`，`AWSC.use("nc")` 会同步调用回调
- 但 punishment bundle 的 `var T` 还没有初始化，导致 `n.init(T)` 时 `T === undefined`
- 真实浏览器中 NC 通常是通过 script 请求异步加载，回调发生在下一轮任务中，T 已经初始化
- iv8 之前没有出现这个问题，很可能是因为它保持了 lazy script loading 或更接近真实的事件时序

**解决方向**：
- 这不是代码层面的 bug，而是 harness 架构设计问题
- 需要在 Evidence Bundle 和 script replay 机制中保持真实的异步加载时序
- 相关工作将在 Phase 3 的 Evidence Loader 和 Replay Fixture 实现中解决
- 确保脚本注入通过异步任务队列，而不是同步 eval

**验证状态**：⚠️ 待 Phase 3 Evidence Loader 实现时解决

##### Bug 3: NV8 的脚本注入/replay 覆盖不完整（已修复）

**问题描述**：
- NC 通过 `insertBefore` 或 DOM 注入创建了 `dss.js`、`wu.json`、`initialize.jsonp` 的 script 节点
- 原来的 NV8 probe 只拦了 `appendChild`，所以看起来像"NC 没有继续请求"
- 补上 `insertBefore` 和 script 节点扫描后，已经能看到这些同轮资源并注入 fixture

**修复方案**：
- 位置：`src/surface/api/dom/node-insert-before.js:26`
- 在 `insertBefore` 方法中添加 `traceCall` 追踪
- 确保 `appendChild` 和 `insertBefore` 都能被 trace 系统捕获

**验证状态**：✅ 已修复并验证
- `src/surface/api/dom/node-append-child.js:21` 已有 `traceCall`
- `src/surface/api/dom/node-insert-before.js:26` 已有 `traceCall`
- 两种 DOM 注入方式都能被正确追踪

##### 影响范围和后续工作

这三类问题的修复对架构改造的影响：

1. **Bug 1 和 Bug 3 已完全修复**，不影响 Phase 3 推进
2. **Bug 2 需要在 Phase 3 的 Evidence Bundle Loader 实现时系统性解决**：
   - Evidence Bundle 必须记录脚本的真实加载时序
   - Replay Fixture 必须通过任务队列而非同步 eval 注入脚本
   - 需要模拟真实浏览器的异步 script loading 行为
3. 这些修复证明了 **trace 系统和 DOM 操作拦截的重要性**
4. 在 Phase 3 需要确保所有 DOM 操作、脚本加载、异步回调都有完整的 trace 覆盖

## 30. 改造完成定义

NV8 改造完成不以目录拆分或插件数量作为标准，而以以下结果为准：

- Core 能在支持矩阵内创建和销毁基础 Realm，且不依赖浏览器能力插件。
- App 可以显式注册插件，输出稳定的依赖/能力/surface lock plan，并在失败时提供
  可行动诊断。
- Window、iframe、Worker、ServiceWorker 和 Worklet 使用同一插件生命周期契约，
  但拥有正确的 Realm-specific surface 和状态隔离。
- 现有常用入口通过 legacy/full Profile 或默认 Profile 保持行为兼容。
- Evidence Loader 能离线、完整、可重复地校验 Bundle；Core 不直接绑定磁盘格式。
- 目标脚本、插件、Core、Protocol 和 Collector 的信任及网络边界可被测试验证。
- reset、snapshot、restore、dispose、超时和后端关闭不泄漏状态或资源句柄。
- Node、backend、Profile、Plugin SDK、Evidence 和 Protocol 的支持矩阵进入 CI。
- 冷启动、reset、内存、并发和关闭指标满足已批准的预算。
- 文档、示例、迁移指南、回滚包和上一版 lock 与代码同时发布。

上述定义满足后，才可以把默认运行模式从 `legacy` 切换到 `plugin`，并开始独立
发布 Core、插件、Profile、Evidence Loader、Protocol 和 Collector 包。
